# Developer Profile API

Backend цифровой визитки Платона Савушкина. GraphQL API возвращает профиль, профессиональные ссылки, навыки, опыт и проекты. Приложение развернуто на VPS и доступно по HTTPS.

**[Открыть API в Apollo Sandbox](https://platon.safeq.studio/graphql)** · **[Healthcheck](https://platon.safeq.studio/health)**

## Проверить API

Откройте Sandbox, вставьте запрос и нажмите Run. Авторизация не требуется.

```graphql
query ProfileCard {
  profile {
    id
    name
    description
    links {
      label
      url
    }
    skills {
      name
      category
    }
    experience {
      company
      position
      startMonth
      endMonth
      achievements
    }
    projects {
      name
      description
      url
    }
  }
}
```

Ответ содержит профиль, 2 ссылки, 20 навыков, 3 записи опыта и 8 проектов. Для проверки выборки отдельных полей можно выполнить `{ profile { name } }`.

Корневой запрос `profile` возвращает `null`, если профиль отсутствует в БД. Успешная GraphQL-операция содержит `data` без `errors`; одного HTTP 200 для проверки недостаточно.

`GET /health` проверяет соединение с PostgreSQL: HTTP 200 и `{"status":"ok"}` при доступной БД, HTTP 503 при ошибке подключения.

## Архитектура и загрузка данных

В API один корневой запрос `profile` без аргументов: визитка представляет одного человека, выбирать профиль по ID не требуется. Ссылки, навыки, опыт и проекты доступны как вложенные поля, поэтому клиент может получить нужные разделы одной операцией.

Code-First позволяет описывать GraphQL-типы декораторами NestJS рядом с resolver и не поддерживать отдельную SDL-схему вручную. Схема строится в памяти при запуске приложения.

```text
GraphQL request
  -> ProfileResolver -> ProfileService -> PrismaService -> PostgreSQL
  -> ResolveField -> DataLoader из request context -> PrismaService
```

Resolver связывает GraphQL-поля с service и loaders. `ProfileService` выбирает публичный профиль, `PrismaService` управляет подключением к БД. Отдельный repository layer не добавлен: нужные операции уже предоставляет типизированный Prisma Client, а дополнительная обертка дублировала бы его методы.

Для каждого HTTP-запроса создаются четыре DataLoader: ссылки, навыки, опыт и проекты. Каждый loader объединяет ID в один `findMany`, восстанавливает порядок результатов и кеширует чтения только в пределах запроса. Следующий запрос получает новый набор loaders.

DataLoader выбран вместо eager `include`, чтобы читать только запрошенные связи и объединять повторные обращения, в том числе через aliases. Для `{ profile { name } }` выполняется одно чтение профиля, для полного ProfileCard - одно чтение профиля и четыре чтения связей. Выбор отдельных скалярных полей внутри связи не меняет запрос к БД: loader читает строки модели связи целиком.

Для проверки API в браузере включен Apollo Sandbox через официальный landing page plugin. Introspection дает подсказки по схеме, GraphiQL отключен. Sandbox доступен и в production; его интерфейс загружается с ресурсов Apollo. 

## Модель данных

[Prisma schema](prisma/schema.prisma) содержит пять моделей: `Profile` и четыре связи 1:N - `ProfessionalLink`, `Skill`, `Experience`, `Project`.

Данные разделены на таблицы, чтобы связи и уникальность записей проверяла БД. PostgreSQL поддерживает внешние ключи, нужные ограничения и транзакционное обновление профиля. Каждый дочерний объект принадлежит одному профилю, общих справочников навыков или проектов в этой задаче нет, поэтому связей many-to-many не требуется.

Дочерние записи имеют стабильные строковые ID, внешний ключ `profileId` и индекс `(profileId, sortOrder)`. Порядок ответа определяется `sortOrder`, затем `id`. Для ссылок и навыков дополнительно заданы уникальные пары `(profileId, label)` и `(profileId, name)`.

Даты опыта хранятся в формате `YYYY-MM`, поскольку исходные данные имеют точность до месяца. `endMonth: null` означает продолжающуюся работу. Достижения хранятся в PostgreSQL `String[]`: это список текстов внутри записи опыта, у них нет собственных полей или связей, для которых нужна отдельная таблица.

[Seed](prisma/seed.ts) проверяет исходные данные и синхронизирует профиль в одной транзакции: upsert родительской записи и замена дочерних. Повторный запуск сохраняет стабильные ID и не создает дубликатов. Ручные изменения этого профиля в БД перезаписываются seed.

## Тестирование

На последней полной проверке прошли **80 unit-тестов и 15 e2e-тестов**, а также TypeScript typecheck, ESLint, Prettier и сборка.

- Unit: конфигурация, валидация seed, service/resolver, batching, порядок результатов и cache DataLoader.
- E2e с реальным PostgreSQL: полный и выборочный GraphQL-запросы, отсутствие лишних чтений связей, aliases, независимость cache между HTTP-запросами, отсутствие mutations и идемпотентность seed.
- Проверки деплоя: миграции, HTTPS, перенаправление HTTP, тест продления сертификата, сохранность данных после перезапуска API и сценарии отката приложения.

E2e используют отдельную БД: перед запуском проверяется `TEST_DATABASE_URL`, имя БД должно заканчиваться на `_test` и отличаться от основной. CI не настроен.

## Deployment

```text
HTTPS -> Nginx -> api:3000 -> db:5432
```

[Production Compose](compose.prod.yaml) поднимает отдельный проект с собственными сетями и volumes. Наружу опубликованы только порты 80/443 Nginx; API и PostgreSQL общаются по Docker-сети. Данные БД хранятся в постоянном volume.

Nginx завершает TLS и перенаправляет HTTP на HTTPS. Сертификат Let's Encrypt продлевается через Certbot и systemd timer. Для контейнеров настроены лимиты ресурсов и ротация логов.

Миграции и seed выполняются в отдельном `init` контейнере до запуска API, чтобы приложение принимало запросы с подготовленной БД. Перезапуск API не запускает seed. Runtime image содержит скомпилированный JavaScript и production dependencies; Prisma CLI остается в образе для инициализации.

[Скрипт деплоя](deploy/deploy.sh) проверяет ресурсы, собирает образы, сохраняет дамп перед миграциями и запускает `init` перед API. Он хранит текущую и предыдущую пары образов и два последних дампа. Откат приложения не откатывает схему БД и требует проверки совместимости. Обновление предусматривает короткий перерыв обслуживания.

## Границы задачи

API публичный, доступен только для чтения и возвращает один профиль. Изменение данных выполняется через seed. Mutations, авторизация, CMS и загрузка файлов не входят в требования тестового задания.

Federation не нужен одному GraphQL-сервису, CQRS не дает пользы при отсутствии операций записи в API. Redis не добавлен, поскольку задачи кеширования между запросами нет. S3 не используется: приложение хранит текст и ссылки, файлы не принимает.
